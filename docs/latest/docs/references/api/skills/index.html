POST /skills.delete​

Description​

Delete a tenant-uploaded skill (tenant-admin only). Platform-assigned skills
cannot be deleted here - they leave the tenant only via un-assignment through
the PMC. Takes effect for listings and downloads immediately; copies agents
already installed persist on their machines.

POST /skills.download​

Description​

Download one skill by name as an installable zip archive. The response is not a
JSON envelope: a successful call answers with raw application/zip bytes holding
/SKILL.md plus / for each auxiliary file the package ships
(see the entry's file_paths). Downloads are authorized exactly like the
listing: a skill hidden from the caller's groups is not downloadable by name
and answers NotFound.

POST /skills.update​

Description​

Update a skill's tenant-local settings (tenant-admin only). The skill's name is
its identity and is never changed here. 'description' edits the catalog
description of a TENANT-UPLOADED skill: it is seeded from the SKILL.md
frontmatter at ingest and catalog-owned thereafter (a re-upload reseeds it from
the new document's frontmatter); a description for a platform skill is rejected

  • it follows the global catalog. 'allowed_groups' restricts which user groups
    see the skill in listings and may fetch or download it, for any skill in the
    tenant: absent = leave unchanged, [] = visible to every company user, otherwise
    visible to members of any listed group (admin and system callers always see
    everything). The configuration is kept per (tenant, skill name), so it survives
    platform-skill un-assignment and re-assignment, and governs a tenant upload
    shadowing a platform skill of the same name.

POST /skills.upload​

Description​

Upload skills scoped to the calling user's own tenant (tenant-admin only). Each
uploaded file must be a single-skill zip (/SKILL.md) or a bare SKILL.md
document; bundles (zip of skill zips) are a platform-admin capability. A skill
zip may ship auxiliary files alongside its SKILL.md (e.g. references/...), all
under the same root; document and files form one atomic package, replaced
together on every upload (a bare SKILL.md is a package with no files, so
uploading one clears any files a previous upload carried). The skill's name and
version are always resolved from the SKILL.md frontmatter - file names play no
part in identity, and a document without a frontmatter 'metadata.version' is
rejected. Upload is atomic (any invalid file rejects the whole upload with per-
file errors) and force-overrides an existing skill of the same name - that is
the update path. Built-in skill names are reserved. Versioning: agents detect
updates by version CHANGE, so an override that keeps an existing skill's
version with different content is rejected - the guard covers the whole
package, document and auxiliary files alike; raise metadata.version (re-
uploading the byte-identical package is accepted as a no- op). Any version
change, lower included, is accepted and propagates. Wire format: a
multipart/form-data POST with one part per file (at most 20 files, 5 MB each);
the part name labels the file in error reports. On rejection the error response
carries meta.error_data.errors as a list of {file, msg} entries, one per
offending file, alongside the joined summary in meta.result_msg.
